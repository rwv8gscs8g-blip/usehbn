## Resumo Humano

1. A branch `proposta/onda-0006` implementa as remediações F-01..F-10 em 13 commits atômicos de forma tecnicamente coerente.
2. Contudo, foi identificado um erro crítico de compatibilidade de Bash no guard `G-TOK` que quebra a suíte de testes (120/121) no macOS.
3. A bateria adversarial reporta 14/14 bloqueadas (falso verde), pois o crash de sintaxe do `G-TOK` retorna exit code 1, mascarando o teste.
4. O runbook da tabela de aprovação possui um deadlock operacional que bloqueia os cherry-picks de `I-12` e `I-09` se o token for gerado no `I-13`.
5. O comando de cherry-pick do runbook sobrescreve a autoria original dos commits para o identity do operador git (Maurício).

7. A proposta do Glacier-move é inexecutável por design, pois gera IDs com agente `glacier`, que é bloqueado pelo guard `G-NUM`.
8. Recomenda-se o veto aos cherry-picks até que as correções de compatibilidade, runbook e renomeação de IDs sejam aplicadas.

#### (e) Correção do cherry-pick do runbook
- **Evidência**: Execução de teste em repositório espelho local.
- **Análise**: **[BLOQUEADOR]** O comando sugerido no runbook `git cherry-pick -n <sha> && git commit --no-edit` dispara corretamente os hooks `pre-commit` e `commit-msg` e preserva a mensagem e trailers originais. No entanto, ele **sobrescreve o autor original do commit** (`claude-fable-5`) com o email/nome local do operador git (`Maurício`). Para preservar a autoria e os metadados de autoria originais do commit enquanto roda as validações dos hooks, o comando correto que o humano deve usar é:
  ```bash
  git cherry-pick -n <sha> && git commit -C <sha>
  ```

### A3 — G-TOK (Posse de Bastão)

- **Evidência**: [guards/assert-baton-token.sh:54-68](file:///Users/macbookpro/Projetos/usehbn/guards/assert-baton-token.sh#L54-L68) e [guards/assert-baton-token.sh:102-108](file:///Users/macbookpro/Projetos/usehbn/guards/assert-baton-token.sh#L102-L108).
- **Análise**: 
  1. **Replay de Token / Logs públicos**: **[FORTE]** O token é gravado em texto plano no commit message como trailer `HBN-Token: <token>`. Assim que o primeiro commit de posse do bastão é feito, o token torna-se público no histórico de git compartilhado. Qualquer outro agente ou invasor pode extrair o token do histórico e assinar commits subsequentes fingindo reter a posse do bastão até que haja uma rotação física da chave. Ao contrário do `G-HRB` (que usa assinaturas SSH assimétricas e nunca vaza a chave privada no log), o `G-TOK` fornece segurança apenas de "porta de entrada", não de retenção de segredo.
  2. **Range em CI**: Em modo CI, o guard lê a variável `bastao_token_sha256` a partir da referência `HEAD:${STATE_PATH}` (o estado final da branch/push). Se um push contiver múltiplos commits em que um deles rotacione o token (e.g. Commit A com token velho, Commit B que rotaciona o token e STATE, Commit C com token novo), os commits anteriores à rotação (A) falharão na verificação do CI porque serão confrontados contra o hash do token novo em `HEAD`.

### A4 — Lacres e Burlas

- **Evidência**: Execução da suíte via `bash guards/tests/run-guard-tests.sh` e `bash guards/tests/adversarial-battery.sh` no macOS.
- **Análise**: 
  1. **Incompatibilidade Bash 3.2**: **[BLOQUEADOR]** O guard `assert-baton-token.sh` na linha 89 realiza a expansão `${EXPECTED,,}` para converter o hash esperado para minúsculas. A versão padrão do Bash no macOS é 3.2, que não aceita essa sintaxe de expansão (introduzida no Bash 4), resultando no erro de execução:
     `guards/assert-baton-token.sh: line 89: ${EXPECTED,,}: bad substitution`
     Isso causa a quebra do teste `tok: token correto → passa` na suíte.
  2. **Falso Verde na Bateria Adversarial**: O teste adversarial `B14 trailer HBN-Token com token errado` reporta `BLOQUEADA ✓`, mas isso é um falso verde. O script `assert-baton-token.sh` quebra por erro de sintaxe e retorna exit code 1. A bateria assume que qualquer retorno diferente de zero indica bloqueio bem-sucedido do caso de burla, falhando em detectar o crash do guard.
  3. **Bypass Env notes**: O mecanismo de bypass exige uma nota em `.hbn/bypasses/`. Contudo, qualquer arquivo novo adicionado a este diretório desativa **todos** os guards simultaneamente no diff, em vez de isolar apenas o guard que motivou o bypass.

- **Veredito**: **REPROVAR**

- **Evidência**: [usehbn-entregas/onda-0006/20260611-162612-fable5-tabela-aprovacao-onda-0006.md](file:///Users/macbookpro/Projetos/usehbn-entregas/onda-0006/20260611-162612-fable5-tabela-aprovacao-onda-0006.md).

Se o humano fizer isso no `I-13`, os commits subsequentes de `I-12` e `I-09` que ele precisa cherry-pickar serão **bloqueados** pelo hook `commit-msg` recém-ativado no `I-13`, já que os commits `5ab9e7b` e `c79fa06` não carregam o trailer `HBN-Token: <token>` em suas mensagens.

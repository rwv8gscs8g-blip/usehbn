## Comportamento exigido (você escreve o bash — §2.10)

Em `guards/assert-orq-entrada-ref.sh`, trocar o bloqueio amplo (`:247-251` e a alça CI `:253-264`)
por uma **triagem de diff** que, num ato de autoridade, PERMITE alterar SOMENTE
`.hbn/attestations/${token_fp}-orq-entrada.json` se TODAS valerem (senão BLOQUEIA, fail-closed):

1. `orq_entrada_ref` do ato == `.hbn/attestations/${token_fp}-orq-entrada.json`, `token_fp` do
   `bastao_token_sha256` do STATE **staged (novo)**.
2. Nenhuma OUTRA atestação `.hbn/attestations/<fp>-orq-entrada.json` add/rm/rename/mod no mesmo ato.
3. **Regeneração real de mesmo-fp**: fp do nome == fp do JSON antigo == fp do JSON novo == fp
   esperado; **`bastao_token_sha256` completo do STATE NÃO mudou** no ato (pega colisão de prefixo);
   `manifest_sha256` novo ≠ antigo; e a nova atestação **passa `assert-orq-entrada.sh`**.
4. **Consistência de proveniência (não-autoritativa)**: `proprietario_bastao` e `identidade` da
   atestação nova == os do HEAD (`HEAD:`/`commit^:`); divergência ⇒ BLOQUEIA.
5. Ambiguidade (blob ausente, JSON ilegível, campo não-string, rename/delete/add, múltiplas
   atestações) ⇒ BLOQUEIA.

**Simetria local/CI obrigatória:** local compara `:path` vs `HEAD:path`; CI compara `${commit}^:path`
vs `${commit}:path` para cada commit em `HBN_DIFF_BASE..HEAD`. Mesma semântica nos dois modos.

**Ordem:** a triagem decide "é regeneração permitida do mesmo bastão?" ANTES de chamar
`assert-orq-entrada.sh` (que decide "a prova extrativa é válida?"). Não basta remover `:247-251`.

**Item aditivo recomendado (raiz do gap do grok):** em `guards/assert-orq-entrada.sh`, cruzar
`proprietario_bastao`/`identidade` da atestação ↔ STATE (hoje só `bastao_token_fp` é checado,
`:274`). Implemente como verificação aditiva e cubra com teste; se julgar que muda demais o contrato
v2, PARE e relate antes — não amplie sozinho para core/schema.

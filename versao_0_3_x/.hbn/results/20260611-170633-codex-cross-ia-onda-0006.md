### (a) Working-tree bootstrap do I-05

Limite técnico: não há hash/log do arquivo de working tree pré-I-00; portanto "o conteúdo commitado no I-05 é exatamente o que rodou desde I-00" não é provável mecanicamente. A adoção por cherry-pick reexecutaria em raiz canônica, então o risco é de rastreabilidade histórica da branch, não de aplicação final.

### (b) Reword via filter-branch

Verificado. Existe `refs/original/refs/heads/proposta/onda-0006` apontando para `74fb55f`. O comando:

`while read old new; do test "$(git show -s --format=%T "$old")" = "$(git show -s --format=%T "$new")" && echo TREE_SAME; done`

com pares `06ecdc0/dfbc5ab` até `74fb55f/2e2a1c1` retornou `TREE_SAME` para os 8 pares. `git diff --quiet "$old^{tree}" "$new^{tree}"` também retornou `no-tree-diff` para todos. A ref original mostra que antes do reword os commits tinham `HBN-Readback` e `HBN-Agent`, mas não `HBN-Human-Authorization`; os novos têm os três trailers (`git log --format='%h %T %P %s%n%(trailers)' --reverse main..proposta/onda-0006`).

## A3 — G-TOK

BLOQUEADOR 1: implementação quebra no Bash do operador. O guard usa fallback de hash em `guards/assert-baton-token.sh:54-59`, lê `bastao_token_sha256` do STATE staged em `:70-79`, extrai `HBN-Token` em `:82-90` e compara com `${EXPECTED,,}` em `:89`. A suíte confirma: `bash guards/tests/run-guard-tests.sh` terminou `120 passaram, 1 falharam` e a falha foi `tok: token correto -> passa — esperado pass, obtido rc=1`.

BLOQUEADOR 2: o desenho não impede posse simultânea depois do primeiro commit tokenizado. `core/state-report-spec.md:108-115` assume que o token usado "morre público no histórico"; mas enquanto o hash do STATE não rotacionar, qualquer agente com acesso ao repositório pode ler o trailer `HBN-Token` do commit anterior e reutilizá-lo. Isso evita adivinhação externa, mas não prova posse exclusiva entre janelas com acesso ao mesmo repo.

Riscos adicionais:

- Replay pós-rotação: se o hash novo for staged corretamente, token antigo falha; se o hash novo existir só na working tree e não no index, `state_content` usa `git show :STATE` em `guards/assert-baton-token.sh:62-67` e a exigência pode continuar ausente.
- Commit sem hook `commit-msg`: localmente ainda é possível por `--no-verify` ou hook ausente; em CI o guard só valida range se for chamado com `HBN_DIFF_BASE`, e `HBN_REQUIRE_BATON_TOKEN=1` não aparece configurado na branch.
- Vazamento: por desenho o token fica no trailer do commit; o próprio spec torna o segredo público após o primeiro uso.

## Achados

### BLOQUEADOR — G-TOK reprova o caso positivo no shell canônico

Evidência: `guards/assert-baton-token.sh:89` usa `${EXPECTED,,}`; `bash --version` retornou `GNU bash, version 3.2.57(1)-release`; teste manual retornou `bad substitution`; `bash guards/tests/run-guard-tests.sh` retornou `tok: token correto -> passa — esperado pass, obtido rc=1`.

### BLOQUEADOR — Runbook de cherry-pick/hook quebra a adoção item a item

Evidência: `.git/hooks/commit-msg:1-4` chama `assert-baton-token.sh` e `assert-exception-traceable.sh`; `git cat-file -e main:guards/assert-baton-token.sh` retornou `fatal: path ... exists on disk, but not in 'main'`; simulação do primeiro cherry-pick com o hook da tabela terminou `rc=1` e `No such file or directory`.

Correção mínima: documentar um hook tolerante a guard ausente até I-13/I-08, ou instalar o hook só no ponto exato em que ambos os scripts já existem no working tree de `main`, e ajustar o comando para `git commit -C <sha>`.

### BLOQUEADOR — G-TOK não prova posse exclusiva após o primeiro commit

Evidência: `core/state-report-spec.md:108-115` exige trailer com token e admite que o token usado fica público no histórico. Enquanto o mesmo hash permanece no STATE, o trailer anterior permite replay por qualquer agente com acesso ao repo.

Correção mínima: tratar o token como nonce de uso único por commit ou usar assinatura/chave local não publicada; no mínimo, declarar que G-TOK é prova de conhecimento momentâneo, não exclusão de posse.

### FORTE — STATE/tabela têm claims falsos de contagem e suíte

Evidência: `.hbn/relay/STATE.md:5`, `.hbn/relay/STATE.md:16`, tabela `:13-15`, comando `git rev-list --count ...` = 13 e `run-guard-tests` = 120/121.

### FORTE — I-04 não prova "só path" por diff

Evidência: `git show ed45fe1` mostra os pareceres como `new file mode 100644`; não há preimage versionado dos seriais 0036/0037. Front-matter atual e REGISTRY conferem, mas a alegação de alteração mínima depende de confiança externa.
